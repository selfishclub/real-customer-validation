# QA 플레이북

> 페르소나가 **말로 평가하는 것**과 **실제로 해보다 막히는 것**은 다르다.
> 이 문서는 후자를 다룬다. **"어디서 막히나"** 와 **"실제로 눌러보면"** 모드에서 반드시 읽는다.

---

## 1. 대원칙

1. **페르소나는 테스터가 아니라 생활인이다.** 버그를 찾으려 애쓰지 않는다. **자기 목적을 이루려다 막힌다.**
2. **막히면 거기서 멈춘다.** 억지로 완주시키지 않는다. 실제 사용자는 포기한다.
3. **"왜 막혔는지"를 사용자 언어로 적는다.** `버튼 대비 부족`이 아니라 **"글씨가 연해서 눌리는 건지 아닌지 몰랐어요."**
4. **되돌릴 수 없는 행동은 하지 않는다.** 제출·결제·가입 완료·발송·삭제 금지. 그 직전에서 멈추고 보고한다.
5. **페르소나 능력 밖의 일은 안 된다.** 저디지털 페르소나가 개발자 도구를 열지 않는다.

---

## 2. 막힘 6유형

| 코드 | 유형 | 정의 | 전형적 발화 | 처방 |
|---|---|---|---|---|
| **B1** | **못 찾음** | 화면에 있는데 발견 못함 | "어디를 눌러야 되는 건지" | 위치·크기·대비 |
| **B2** | **못 알아봄** | 봤지만 의미를 모름 | "온보딩이 뭔데요" | 용어·카피 |
| **B3** | **못 믿음** | 이해했지만 신뢰가 안 섬 | "전화번호를 왜 적어요" | 근거·최소수집 |
| **B4** | **못 함** | 조작이 실패함 | "눌렀는데 아무것도 안 되던데요" | 인터랙션·반응성 |
| **B5** | **안 함** | 할 수 있는데 **할 이유가 없음** | "할 수는 있는데… 굳이요?" | 가치제안·타이밍 |
| **B6** | **끊김** | 기술적 실패 | 404 · 에러 · 무한 로딩 | 버그 수정 |

### B5가 이 모드의 존재 이유다

일반 QA는 **"되는가"**를 본다. B1·B4·B6은 개발자도 잡는다.
**B5는 기능이 완벽해도 발생한다.** 다 되는데 아무도 안 누르는 상태.
**B5가 나왔으면 리포트 최상단에 올린다.**

> **B5는 검증 파트의 R2(우선순위 낮음)와 짝을 이룬다.**
> 흐름에서 B5가 나오고 인터뷰에서 R2가 나오면, 같은 문제를 두 각도에서 본 것이다.

### 분류가 애매할 때

| 헷갈림 | 판정 기준 |
|---|---|
| B1 vs B2 | **눈이 못 찾았으면 B1, 눈은 찾았는데 머리가 못 따라갔으면 B2** |
| B2 vs B5 | **이해를 못 해서 멈췄으면 B2, 이해했는데 안 했으면 B5** |
| B3 vs B5 | **불안해서 멈췄으면 B3, 무덤덤하게 안 했으면 B5** |
| B4 vs B6 | **내 조작이 틀린 것 같으면 B4, 시스템이 깨진 것 같으면 B6** |

## 3. 심각도 3단계

| 등급 | 이름 | 정의 |
|---|---|---|
| **S1** | **이탈** | 여기서 나갔다. 다시 안 온다 |
| **S2** | **지연** | 헤맸지만 결국 통과했다 |
| **S3** | **잔여 불쾌** | 완료는 했는데 찜찜함이 남았다 |

**S1이 하나라도 있으면 그것부터 고친다.** S2 열 개보다 S1 하나가 비싸다.

---

## 4. 모드 · 어디서 막히나 (문서 기반)

**어디서든 된다.** 브라우저 접근이 없어도 실행 가능.

### 입력

- 단계 나열 (링크 → 상세페이지 → 신청폼 → 완료)
- 스크린샷 (순서대로)
- 랜딩페이지 텍스트 전문

### 패널 3명

| 자리 | 누구 | 왜 |
|---|---|---|
| 1 | **고CLV 찐고객** | 정상 경로 확인 |
| 2 | **저디지털 또는 접근성** | 조작 한계 노출 |
| 3 | **회의적 또는 약관정독** | B3·B5를 가장 잘 잡음 |

### 각 단계에서 넷 중 하나로 반응

```
통과   — "다음 눌렀어요"
머뭇   — "여기서 잠깐 헷갈렸는데…" + 이유
막힘   — "여기서 멈췄어요" + 이유 (계속은 함)
이탈   — "여기서 껐어요" + 이유 (여기서 종료)
```

**이탈하면 그 페르소나의 워크스루는 끝이다.** 나머지 단계를 상상해서 채우지 않는다.

### 반드시 물어야 할 3+1

1. **지금 뭘 하라는 화면인가요?** → B2 감지
2. **다음에 뭘 눌러야 하나요?** → B1 감지
3. **하고 싶으세요?** → **B5 감지**
4. (개인정보·결제 단계만) **여기다 이걸 적어도 괜찮으세요?** → B3 감지

## 5. 모드 · 실제로 눌러보면 (라이브)

**브라우저 도구가 있을 때만.** 없으면 문서 기반으로 폴백한다.

### 안전 규칙

| 해도 되는 것 | **절대 안 되는 것** |
|---|---|
| 페이지 열기 · 읽기 | **폼 최종 제출** |
| 스크롤 · 클릭(이동) | **결제 · 구매** |
| 스크린샷 | **회원가입 완료** |
| 입력칸에 테스트값 타이핑 | **메일·알림 발송** |
| | **삭제 · 취소 버튼** |

> **되돌릴 수 없는 행동 직전에서 멈춘다.**
> "여기서 멈췄습니다. 실제 제출은 하지 않았어요"로 보고한다.

### 페르소나 눈으로 본다는 것

| 태그 | 어떻게 다르게 보나 |
|---|---|
| 저디지털 | 화면 상단만 본다. 아이콘만 있는 버튼은 못 알아본다 |
| 접근성 | 작은 글씨를 못 읽는다. 연한 회색은 없는 것과 같다 |
| 보안민감 | 입력 필드를 보면 "이걸 왜 받지"부터 생각한다 |
| 약관정독 | 실제로 약관을 연다. 없거나 깨져 있으면 그 자체가 막힘 |
| 회의적 | 새 개념이 나오면 "기존 방식 대비 뭐가 나은지"부터 따진다 |
| 고디지털 | 빠르게 훑는다. 대신 **어색한 지점을 정확히 짚는다** |

## 6. 리포트 양식

```markdown
## QA 리포트 — (프로덕트명)

**대상**: (URL 또는 흐름 이름)
**패널**: (이름 · 나이 · 직업 · 태그) × N
**방식**: 문서 기반 / 실제 브라우저

### 단계별 통과 현황

| 단계 | 페르소나1 | 페르소나2 | 페르소나3 |
|---|:---:|:---:|:---:|
| 1. 랜딩 진입 | 통과 | 머뭇 | 통과 |
| 2. 내용 이해 | 통과 | **이탈 B2/S1** | 머뭇 |
| 3. 신청 버튼 | 머뭇 | — | **이탈 B5/S1** |

*— 는 이미 이탈해서 도달하지 못함*

### 막힘 상세

| # | 유형 | 심각도 | 어디서 | 누가 | 그 사람 말 | 처방 |
|---|---|---|---|---|---|---|
| 1 | **B5** | **S1** | 신청 버튼 | … | "할 수는 있는데, 지금 해야 할 이유를 모르겠어요" | 마감·혜택을 버튼 옆에 |

### 먼저 고칠 것 3개
1. **(S1)** …
2. **(S1)** …
3. **(S2)** …

### 확인하지 못한 것
- (실제 결제 흐름 — 안전 규칙상 미진행)
- (모바일 화면 — 데스크톱만 확인)
```

## 7. 흔한 실수

| 실수 | 왜 문제인가 |
|---|---|
| 페르소나가 버그를 "찾으러" 다님 | 실제 사용자는 버그를 찾지 않는다 |
| 이탈한 페르소나를 계속 진행시킴 | 그 뒤 데이터는 전부 허구다 |
| 막힘을 전부 B1로 분류 | 처방이 "버튼 키우기"로만 수렴한다 |
| **B5를 리포트에서 뺌** | **가장 비싼 문제를 빠뜨리는 것** |
| 개선안까지 페르소나가 말함 | 증상은 페르소나가, 처방은 리포트가 |
| 실제 폼을 제출함 | 안전 규칙 위반 |
